# Enemy Return - Design Document

## Overview

This document describes the design of the Enemy Return feature.

The purpose of this feature is to allow enemies to return to their original spawn position after the player has escaped their detection range.

Enemy Return restores the enemy to its patrol area and transfers control back to the Enemy Patrol module once the destination has been reached.

This feature completes the passive AI cycle by connecting Enemy Chase with Enemy Patrol.

Enemy Return does not implement combat, detection, pathfinding, or backend communication.

---

## Architecture

Enemy Return introduces a dedicated Return Controller responsible for moving an enemy back to its original spawn position.

The Return Controller listens for state changes generated by the Chase Controller. Once pursuit ends, it begins moving the enemy toward its stored spawn position until the destination is reached.

After arriving at the spawn position, the Return Controller stops movement and transfers control back to the Patrol Controller.

### High-Level Architecture

```text
             Detection Controller
                      │
               PlayerDetected
                      │
                      ▼
              Chase Controller
                      │
                PlayerLost
                      │
                      ▼
             Return Controller
                      │
        Return To Spawn Position
                      │
          Destination Reached
                      │
                      ▼
             Patrol Controller
                      │
                      ▼
           Enemy Patrol Behavior
```

The Return Controller is responsible only for returning the enemy to its spawn position.

Patrol behavior remains fully managed by the Patrol Controller.

---

## Components and Interfaces

### Enemy

**Responsibilities**

- Store the current world position.
- Store the original spawn position.
- Store the current movement state.
- Store the current facing direction.
- Expose movement operations.

Enemy must not calculate return behavior.

---

### Return Controller

**Responsibilities**

- Listen for chase completion events.
- Start the return process.
- Calculate movement toward the spawn position.
- Stop movement after reaching the destination.
- Transfer control back to the Patrol Controller.
- Update enemy movement state and direction.

The Return Controller contains all return logic.

---

### Chase Controller

**Responsibilities**

- Notify when pursuit ends.
- Trigger the Return Controller.

The Chase Controller remains responsible only for pursuit.

---

### Patrol Controller

**Responsibilities**

- Resume patrol after the return process completes.
- Continue autonomous patrol from the spawn area.

Patrol logic remains independent from Return.

---

### Enemy Animation Module

**Responsibilities**

- Play walking animations while returning.
- Play idle animations after arrival.
- Update animations according to movement direction.

Enemy Return never communicates directly with Phaser's animation system.

---

### MainScene

**Responsibilities**

- Create one Return Controller per enemy.
- Update every Return Controller during the game loop.
- Coordinate controller lifecycle.

MainScene must never contain return logic.

---

## Data Models

### Return State

Supported values:

```text
Inactive

Returning
```

The Return Controller transitions between these states according to Chase Controller events.

---

### Spawn Position

Represents the original position where the enemy was created.

```text
spawnX

spawnY
```

The spawn position is stored once when the enemy is spawned and never changes.

---

### Return Target

Represents the destination used by the Return Controller.

```text
targetX = spawnX

targetY = spawnY
```

The Return Controller always returns the enemy to its stored spawn position.

---

### Return Speed

Represents the movement speed while returning.

```text
returnSpeed
```

The return speed is configurable independently from patrol and chase speeds.

---

## Correctness Properties

The following invariants must always hold:

- Enemy Return must begin only after the Chase Controller reports that pursuit has ended.
- The original spawn position must remain immutable during gameplay.
- Return movement must always target the stored spawn position.
- Enemy direction must always reflect movement direction while returning.
- Enemy animations must remain synchronized with movement.
- Enemy Return must never invoke Phaser animations directly.
- Enemy Return must never perform player detection.
- Enemy Return must never perform combat.
- Enemy Return must never communicate with the backend.
- Patrol must resume automatically after the enemy reaches its spawn position.
- Return logic must remain independent from Patrol, Detection, and Combat.

---

## Error Handling

The system shall gracefully handle the following situations:

- Missing enemy reference.
- Missing spawn position.
- Invalid return target.
- Invalid movement state.
- Unexpected return failures.

Whenever the return process cannot continue safely, the enemy shall stop moving and remain idle.

The scene must never terminate because of return failures.

---

## Testing Strategy

### Unit Testing

Verify that:

- Return begins after chase ends.
- The stored spawn position is used as the return target.
- Enemy movement is calculated correctly.
- Enemy direction updates correctly.
- Return completes when the destination is reached.
- Invalid spawn positions are handled safely.

---

### Integration Testing

Verify that:

- Chase Controller correctly activates the Return Controller.
- Returning enemies move back to their original spawn position.
- Patrol resumes automatically after return completes.
- Walking and idle animations remain synchronized.
- Multiple enemies return independently.

---

### End-to-End Testing

Verify that:

- Enemies begin returning immediately after losing the player.
- Returning enemies continuously move toward their original spawn position.
- Patrol automatically resumes after arrival.
- Enemy animations remain synchronized throughout the return process.
- Multiple enemies return independently without interfering with one another.
- Enemy Return remains independent from Detection, Combat, backend communication, and pathfinding.
